上周写了个小脚本，把日志里的时间戳换算成人类可读的日期。测试通过，上线，图上显示的时间全是八小时前的。

我盯着代码看了很久。`new Date(ts)` 这么简单的调用，能错在哪。

## 错在单位

日志里的时间戳是秒，`Date` 要的是毫秒。

```js
const d = new Date(log.ts);        // 2026-01-19... 为什么是1970？
const d = new Date(log.ts * 1000); // 对了
```

`new Date(1750000000)` 会把 1750000000 当成毫秒，也就是 1970 年 1 月 20 日附近。它不会报错，因为那是个合法的时间。这类 bug 最麻烦的地方就在这里——**它不崩，它只是安静地给出错的答案**。

## 错在时区

第二个问题更隐蔽。我以为 `new Date(x).toISOString()` 拿到的是本地时间，其实拿到的是 UTC。

```js
const d = new Date(1750000000 * 1000);
d.toISOString();      // 2026-06-15T17:46:40.000Z  ← UTC
d.toLocaleString();   // 取决于运行环境的 locale
```

所以在服务器上（UTC）打印出来和在本机（东八区）打印出来，差八小时。不是代码有问题，是两边的"本地"不一样。

## 怎么避免

我现在给自己定了几条：

1. **存时间一律存 UTC 或带时区的 ISO 8601**，不存模糊的本地字符串。
2. **函数签名里带上单位**。不叫 `ts`，叫 `tsSeconds` 或 `tsMillis`。类型系统帮不了你，命名可以。
3. **不要在服务器和客户端各信一套时区**。要显示本地时间，就在最后一步、在浏览器里转。
4. **跨时区比较，一律先转成同一基准**。

## 一个可用的工具函数

```js
// 接受秒、毫秒、或字符串，统一返回毫秒
function toMillis(input) {
  if (typeof input === 'number') {
    // 13 位是毫秒，10 位是秒
    return String(input).length <= 10 ? input * 1000 : input;
  }
  const t = Date.parse(input);
  if (Number.isNaN(t)) throw new Error(`无法解析时间: ${input}`);
  return t;
}
```

这个判断不严谨——理论上秒数可以有很多位——但对日志场景够用。真要严谨，就别猜，让对方明确给单位。
